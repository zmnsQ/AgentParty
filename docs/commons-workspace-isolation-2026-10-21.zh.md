# Commons 补充审查：工作区隔离与 GitHub 写入前授权

日期：2026-10-21。基线：`4d0ea5e2d340a0652b080e005a02e3d3d454f45a`。

本次在已提交的租约与撤销修复之上继续改进，不覆盖已有分支历史，不改变供应商支持承诺。

## 本次修复

| 场景 | 处理方式 |
| --- | --- |
| 切换群组、登录身份或服务器时，旧群数据和管理控件仍留在页面 | 将协作摘要绑定到 token、群组、服务器与 client 的作用域；新作用域立即卸载旧内容及草稿，迟到响应不能恢复旧数据 |
| 旧组件保存完成后调用刷新，可能向新服务器刷新旧群 | 回调执行前检查当前作用域及 API 地址；过期回调不再发起请求 |
| 当前群权限被撤销，刷新失败却保留旧的私有信息和操作控件 | 对真实 `AuthError` / `ForbiddenError` 及明确的 401/403/404/410 清除当前摘要，不把授权失败伪装成空列表 |
| 上传尚未完成就离开页面、切服务器或失去上传权，随后仍自动投递文件 | 上传完成后再次核对作用域、组件生命周期及权限；阻止后续群投递和剩余文件操作 |
| 旧 GitHub 发布者丢失租约后，虽然不能更新本地状态，仍可能继续发起远端写入 | 在创建树、提交、专用分支及 draft PR 的每次 POST 前核验并续期当前请求所有权；已过期或被接管则停止后续写入 |
| 无法确认写入权限时泄露内部错误或误称确定失败 | 检查失败时不发送写请求；错误不包含底层异常/凭据；已经发生写入的操作继续保留不确定结果语义 |

已在此前提交实现的随机租约、原子撤销、完成态保护和回执恢复继续保留。本次额外补充取消与旧轮询竞争、加锁后重新读取状态、相同请求 ID 并发提交，以及写入前租约过期/接管的回归用例。

## 升级与边界

本次没有新增依赖或数据库迁移；从最初预览升级仍必须先执行上一轮的 `0048_collaboration_lease_fencing.sql`，并按 [迁移说明](commons-hardening-2026-10-21.zh.md) 排空旧写入请求。不要将旧的无所有权检查写入者与新版本长期混跑。

离开页面阻止的是**后续操作**，不是撤回已发送的上传/群消息。GitHub 写入前检查缩小权限失效窗口，但无法撤销已发出的网络请求，也不提供跨服务原子事务。最终群消息仍受 10 分钟去重窗口限制。

本次未使用真实 Hermes/Manus 付费账号运行任务，未在产品内对真实 GitHub 仓库验收发布，没有部署生产服务、远端迁移、触发 GitHub Actions、发布 Release 或编译签名安装包。macOS 上的源码/网页测试不等于 macOS 与 Windows 原生安装验收。原 LICENSE、NOTICE、品牌隔离和手动构建工作流保持不变。

下一优先级仍是单条真实端到端路径（群组 → Agent → 结果/代码提案 → 人工批准 → draft PR），随后是持久任务调度与预算限制、dot/Muse/Grok 账号侧授权，以及原生客户端验证。
